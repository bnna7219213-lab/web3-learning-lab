# 02 · 哈希与雪崩效应：为什么"只上哈希"就够了

> 代码：`frontend/lib/crypto.js`、`frontend/views/hash.js`、`demos/avalanche.mjs`
> 对应思维导图：区块链基础 → How → Hash 算法 ★★★

## 三条性质（缺一不可）

| 性质 | 含义 | 破坏后果 |
|------|------|----------|
| 定长 | 任意原文 → 256 比特 | 无法用固定字段存证、无法比较 |
| 单向 | 从指纹反推原文不现实 | 哈希可当"密码存储"的错误用法会被推翻 |
| 雪崩 | 改 1 比特 → 约一半比特翻转 | 局部改动可被掩盖，篡改检测失效 |

实测（`node demos/avalanche.mjs`）：59 字符逐位翻转，平均 **130.0/256** 比特变化，最少 115、最多 161 —— 与理想值 128 一致。

## 碰撞与生日界

要求前缀 `n` 个十六进制位相同的期望尝试 ≈ `1.2 × 16^(n/2)`（Demo 里 3 位实测 88 次命中）。
完整 256 位碰撞的搜索量级约 `2^128` 次 —— 所以"两个指纹相同 = 两份文件相同"在工程上成立。

前提：**用够强的算法**。MD5/SHA-1 已被实际碰撞攻破，出证材料不能再用。

## 工程约定（跨系统对接时最容易翻车的三件事）

1. **序列化必须规范化**：`H(a|b)` 与 `H(b|a)` 不同；字段顺序、分隔符、编码（UTF-8）、数值精度都要写进接口文档。
   本仓库用 `deviceId|ts|seq|payload|chainId|contract`（见 `lib/sign.js: devicePreimage`）。
2. **域分隔**：叶子与内部节点用不同前缀（`L|` / `N|`），否则"一段数据既能当叶子又能当内部节点"会引入二像问题。
3. **链上链下算法不同**：以太坊用 `keccak256`（不是 `sha256`），比特币用双 `SHA256`。同一份"指纹"跨系统时必须声明算法。

## 商业含义（M4 企业可信档案）

- 原文不出企业内网：链上只有 32 字节指纹 + 脱敏元数据 → 天然满足数据最小化与不出境要求。
- 出证成本与原文大小无关：合同、检测报告、发票影像都是同一个成本量级。
- 客户质疑"你们后台能不能偷偷改"：答"改一个字指纹就变，且我们写入的 root 已锚定在你们也持有的副本/公链上"。
