# 02 · B03 × B07 预算治理衔接（额度上链 + 用量链上派生）

> 2026-11-13 落地。这一轮把「每日额度」从**服务端常量 + 本地记账**搬到了**链上**，
> 并把「凭证发放」挂到了水龙头的当日预算上。
> 目标是让「链上可验证」这条原则在额度治理上也成立 —— 不只是「余额 > 0」这一条前置条件。

## 1. 上一轮的问题

B03 水龙头原先的口径是：

| 东西 | 位置 | 谁能改 |
|---|---|---|
| 每日 500 B03 额度上限 | `faucet/server.js` 里的 `DAILY_BUDGET` 常量 | 改代码 / 改环境变量 |
| 今日已发放多少 | `faucet/data/claims.json` 的 `spent` 字段 | **直接改文件** |
| 每地址 60s 冷却 | `claims.json` 的 `lastClaim` | 直接改文件 |
| 每日 100 份凭证配额 | `credential-service.js` 的 `DAILY_QUOTA` + 本地 `issued` | 改文件 |

B07 发证服务原先的「领证前置条件」是**链上可验证**的（链上余额 > 0），
但**额度**这一层仍然是服务端记账 —— 两套口径不一致：前置条件信链上，额度信文件。

## 2. 为什么不能只改服务端（实测结论）

本轮先做了实测，结论直接决定了方案：

| 探测 | 结果 | 影响 |
|---|---|---|
| `eth_getBalance(addr, 旧块)` | 返回 `null` | Besu 侧历史状态被剪枝，只有 `latest` 可读 |
| `eth_call(nextId(), 旧块)` | `missing revert data` | 读不到「日切时刻的 nextId」 |
| 原生转账的历史日志 | 无（原生转账不产生日志） | 没法用 `eth_getLogs` 查水龙头发币 |
| 逐块扫当日区块统计出账 | 12 562 块要 ~195 s | 当日用量没法实时回算 |
| `eth_getLogs` 单次区间上限 | 5 000 块（10 000 报 `could not coalesce error`） | 日志查询必须分块 |

也就是说：**服务端没有可靠办法从链上回算「当日已发放多少」**。
若额度仍由本地记账决定，改一下 `claims.json` 就能把额度重置。

→ 所以额度本身必须上链（`LabFaucet`），让「用了多少」成为链上状态而不是本地推算值。

## 3. 新架构

```
用户「领币」
   │
   ├─→ B03 faucet(8560)  ── claim(address) ──→ 链上额度合约 LabFaucet
   │        · 额度/冷却/单次金额全在链上强制                 │
   │        · 本地 claims.json 降级为审计流水                │ Payout 事件
   │                                                      ▼
   └─→ 回调 B07 发证服务(8580)
            · 链上余额 > 0（原有前置条件）
            · 当日服务发放份数（链上按签发者派生）< 100
            · 水龙头链上剩余额度 ≥ 10 B03   ← 本轮新增的联动
                        │
                        └─→ mintBatch → CredentialIssued 事件
```

### 3.1 合约 LabFaucet（B07/src/LabFaucet.sol）

| 能力 | 说明 |
|---|---|
| `claim(to)` | 链上强制：当日额度、单次金额、每地址冷却、合约余额 |
| `dailyInfo()` | 当日已发放 / 剩余 / 上限 / 单次金额 / 合约余额（一次 `eth_call` 读全） |
| `claimable(to)` | 只读预检，返回原因码（地址非法 / 政策暂停 / 额度用尽 / 冷却中 / 余额不足） |
| `setPolicy(cap, amount, cooldown)` | admin 链上改治理参数，事件留痕（`PolicyUpdated`） |
| `fund()` / `receive()` | 充值（普通转账直接打进合约地址也行，不会丢账） |
| `Payout(to, amount, day, spentAfter)` | 每次发放留痕 → 当日用量可从事件独立复核 |

- 额度按 **UTC 日切**：`day = block.timestamp / 1 days`，与服务端 `utcDay()` 同口径。
- `dailyCap = 0` 是合法的「暂停发放」姿态（链上一键停）。
- 合约自己持币（已充值 10 000 B03），发放是链上转账，不再是 EOA 直转。

### 3.2 服务侧改造

**B03 faucet（`projects/B03-链上交互实战联盟网/faucet/server.js`）**

- `POST /claim`：先 `claimable()` 预检 → 再 `claim()` 上链 → 响应里的 `budget.source = "chain"`。
- `GET /status`（新增）：链上额度 + 本地审计流水**分开摆**，并注明「本地流水只用于审计」。
- `GET /health`：探链 + 报出额度合约地址与 operator。
- 冷却与额度**不再由服务端判定** → 改本地文件既不能放行、也不能多发。

**B07 发证服务（`projects/B07-NFT市场联盟网/scripts/credential-service.js`）**

- 每日配额：当日**由服务签发账户签发**的份数（链上 `CredentialIssued` 事件按 issuer 过滤后累计 count）。
- 新增水龙头联动：`chainFaucetBudget().remaining < amountPerClaim` → 429「水龙头今日额度已用完，暂停发证」。
- `GET /status`（增强）：链上当日已发数、完整性自检、水龙头额度、本地审计计数。

### 3.3 为什么要给服务一个独立签发账户

链上派生「当日发放份数」时，必须能把两件事分开：

- 用户领取路径（发证服务签发，每次 1 份）
- 运营方批量发行（`05-batch-1000.js` 一次 1000 份）

原先两者都用 `ISSUER_PRIVATE_KEY`。若按「全链当日签发总数」算，
批量测试一次就把当日服务配额占满，**用户领取路径会被锁死**（本轮实测：全链 2 045 份 > 配额 100）。
所以给服务配了专用签发账户 `0xA353D97233B85734f5462BbF76362e635Ad2281B`
（`MINTER_ROLE` + `DEFAULT_ADMIN_ROLE`，由 `scripts/11-grant-service-issuer.js` 授予），
链上按 issuer 过滤即可分开统计：

```
/status → dayIssued: 1              ← 本服务当日签发（配额判定用这个）
          dayIssuedAllIssuers: 2046  ← 全链当日签发（含运营方批量发行）
```

## 4. 怎么改额度（链上治理，不重启服务）

```js
// 运营方：把每日额度改成 1000 B03、单次 20 B03、冷却 120s
const f = new ethers.Contract(FAUCET_ADDR, ABI, adminSigner);
const tx = await f.setPolicy(
  ethers.parseEther("1000"),
  ethers.parseEther("20"),
  120,
  { gasLimit: 200000n, gasPrice: 0n, type: 0 }   // 联盟网零 gas + legacy
);
```

改完立刻生效，两个服务下一次读到的就是新额度（它们读的是链上 `dailyInfo()`）。
把 `dailyCap` 设成 `0` 即暂停发放。

## 5. 验收

`scripts/09-budget-governance.js`（30 项断言全绿）覆盖：

**正例**
- 链上额度口径 = `dailyInfo()`；领币后链上 `spent` +10、剩余相应减少
- 同一次领取带回凭证；当日服务发放份数（链上按签发者派生）0 → 1
- 事件日志完整性自检：全历史 count 合计 == `nextId`（说明日志没被剪枝，派生可信）

**负例**

| 编号 | 攻击/异常 | 期望 | 实测 |
|---|---|---|---|
| A | 伪造水龙头本地记账（写成「今日已发满 500 B03」）并重启服务 | 仍按链上额度放行 | PASS |
| B | 绕过 HTTP 直接调合约 `claim()` | 服务侧随即被**链上冷却**拦下（429） | PASS |
| C | 链上 `dailyCap` 调到已发放额（剩余 0） | 领币 429 + **发证也 429**（联动生效） | PASS |
| D | 伪造发证服务本地记账（`issued = 999999`）并重启服务 | 仍按链上口径发证成功 | PASS |

负例 A / D 特意用「**带伪造文件拉起独立实例**」的方式测，
因为服务启动时会把记账读进内存 —— 只改文件不改进程，断言会假通过。

## 6. 本轮踩到的坑

1. **`JSON.stringify` 不能直接序列化 BigInt**：链上额度都是 BigInt，
   直接拼响应会抛 `TypeError: Do not know how to serialize a BigInt`。
   两个服务的 `json()` 都加了 replacer（BigInt → 字符串）。
2. **异步处理里抛异常会打死进程**：发证服务 `/status` 分支原先没有 try/catch，
   BigInt 序列化异常直接变成 unhandledRejection → Node 结束进程 → 后续请求全部 `fetch failed`。
   现在 `/status` 自己兜异常，进程级再兜一层 `unhandledRejection`（只记日志不退出）。
3. **合约没有 `receive()` 会让充值 revert**：普通转账打不进没有 fallback 的合约。
   已补 `receive()`（与 `fund()` 等价）。
4. **`.ps1` 必须纯 ASCII**：PowerShell 5.1 按 GBK 读无 BOM 的 `.ps1`，
   脚本里写中文路径会变成乱码 → 复制 ABI 时建出了 `B03-閾句笂浜や...` 垃圾目录。
   现在部署脚本用 `B03-*` 通配符定位项目目录。
5. **PowerShell 的 `cd` 不影响 .NET 的当前目录**：`[System.IO.File]::ReadAllText("相对路径")`
   用的是进程启动时的 CWD → 读错文件。绝对路径才稳。

## 7. 边界与后续

- **当前口径**：每日额度 = 链上 `dailyCap`；凭证配额 = 当日**服务签发**份数 < 100；
  两者是「取更严的那个」关系（发证还额外要求水龙头剩余额度 ≥ 10 B03）。
- **还没做的**：
  - 每地址**每日**领取上限（目前只有 60s 冷却，单地址理论上能领满全局额度）→ 合约加一条 `claimedByDay` 即可；
  - 水龙头余额告警（合约余额低于阈值时告警）；
  - 多签治理（现在 `admin` 是单账户 EOA）。
- **兼容性**：旧的 `claims.json`（`{day, spent}` 格式）会被忽略，新格式是 `{claims: [...]}`；
  旧的 B03 索引器/explorer 只读链上数据，不受影响。
