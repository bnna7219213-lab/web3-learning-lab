# 03 · 多成员升级演练：全成员参与窗口 + 回滚方案

> 代码：`scripts/07-upgrade-drill.js`、`script/Upgrade.s.sol`｜实测记录：`deployments/upgrade-drill.json`（2026-11-13）
> 对应 README 验收「一次代理升级演练含全成员参与与回滚方案」；公链 P08 只做 owner 单方升级，联盟链必须做**变更流程**。

## 1. 联盟链升级 ≠ owner 单方行为

README 差异表的原话：「多成员窗口：停机/灰度/回滚需协调，写进变更流程」。演练拆成六步：

| 步骤 | 动作 | 实测断言 |
|------|------|----------|
| 1 变更单 | manifest：代理地址 / 目标实现 / 回滚实现 / chainId / 停机窗口 | 变更单落演练记录 |
| 2 签名窗口 | memberA + memberB 各自签署变更单 | 两个成员签名验证通过；outsider 签名不进签名集 |
| 3 升级前快照 | ERC-1967 实现槽 + slot2(totalDeposited) + owner + version | 快照入记录 |
| 4 升级执行 | owner 部署 VaultV2 → `upgradeToAndCall` | 实现槽指向 V2；**slot2 未漂移**；owner 未变 |
| 5 灰度核对 | V2 新字段 `totalWithdrawn()` / `lastDepositBlock()` 只读可调 | 新能力可用（未跑 migrateFromV1，存储保持 V1 语义） |
| 6 回滚演练 | `upgradeToAndCall` 回 V1 实现 | 实现槽回 V1；slot2 仍未漂移；V1 `deposit()` 业务恢复 |

实测结果：13/13 断言全过（`node scripts/07-upgrade-drill.js`）。

## 2. 两条演练教出来的硬结论

**① 代码可回滚，存储不回滚。**
回滚只是把 ERC-1967 实现槽指回旧实现——V2 期间写过的存储（如 `migrateFromV1()` 把 version 改成 2）
会**留在链上**。所以回滚方案必须配套数据订正，或者像本演练一样「升级期不动数据、迁移后不回滚只前滚」。
演练记录的 conclusion 字段写死了这句话，交付给客户时直接引用。

**② 代理升级后入口不变、ABI 变了。**
V2 新字段要用 **V2 ABI 挂代理地址**读——用旧 ABI 调新函数直接报「不是函数」。
（这也是升级后前端/脚本必须同步换 ABI 的原因，B08 的 `abi/vaultV2.json` 就是为此导出的。）

## 3. 与 storage-layout 门禁的关系

升级前的静态门禁还是 P08 的口径：`forge inspect VaultV1/VaultV2 storage-layout` diff 只允许「吃 gap」，
`Upgrade.s.sol` 内置 slot2 前后对账、变了直接 revert。联盟链新增的是**流程门禁**（签名窗口），
两层合起来才是「多成员窗口」的完整含义：技术上不破坏存储，流程上全员知情。
