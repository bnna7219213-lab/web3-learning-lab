# 07 · B08 × B09 联动

> 一句话：**B08 的链上工程动作（升级 / 空投 / CREATE2 落址）进 B09 的同一个索引，
> 于是"谁在什么时候改了合约"从演练日志变成了可查询、可对账的数据。**
>
> 依赖关系的完整论证见 [`shared/consortium-network/docs/05-B08-B09依赖关系与联动.md`](../../../shared/consortium-network/docs/05-B08-B09依赖关系与联动.md)。

## 一、为什么这件事值得单独做

B08 与 B09 原本是**并列**的两条线：B08 管合约工程，B09 管数据平台。
但联盟链上有一类东西，既不是"业务数据"也不是"合约代码"，而是**运维痕迹**：

| 工程动作 | 链上痕迹 | 以前只能在哪看到 |
|----------|----------|------------------|
| UUPS 代理升级 / 回滚 | `Upgraded(address indexed implementation)`（ERC-1967） | 只有 B08 演练脚本的控制台输出 |
| Merkle 空投领取 | `Claimed(bytes32 leafHash, address indexed to, string data)` | 只有 B08 脚本日志 |
| CREATE2 落址 | `Deployed(address indexed addr, bytes32 indexed salt, uint256 deployCount)` | 只有 B08 脚本日志 |
| Vault 出金 | `Withdrawn(address indexed who, uint256 amount)` | 没有 |

这些痕迹一旦进索引，就获得了三样东西：

1. **可查询**：看板按事件名/合约/地址筛，不用再翻日志；
2. **可对账**：索引条数可以跟链上 `eth_getLogs` 逐条复核；
3. **可跨项目对账**：索引出的实现地址，能跟 B08 自己落盘的升级演练快照对账——
   这一条是本节最有价值的断言，因为它跨了两个独立交付物的边界。

## 二、联动怎么落地（两侧各改了什么）

### B08 侧：把事件暴露出来

| 落点 | 说明 |
|------|------|
| `frontend/server.js:engineeringEvents()` | BFF 直读 `eth_getLogs`，用本地事件注册表解码 `Upgraded`/`Claimed`/`Deployed`/`Withdrawn`/`Initialized`/`OwnershipTransferred` |
| `frontend/server.js:create2State()` | 从最近一次 `Deployed` 事件取 salt → 回查 `deployedBySalt(salt)` → 与事件里的地址对账 |
| `deployments/latest.json` | 事件源地址由部署记录提供（B09 直接读这个文件） |
| `deployments/upgrade-drill.json` | 演练快照（before / after-upgrade / after-rollback 的 impl 地址）——**跨项目对账的参照物** |

### B09 侧：把 B08 的合约纳入监控

| 落点 | 说明 |
|------|------|
| `indexer/config.js:watchSources()` | 事件源清单：B07 的两个合约 **+** B08 的 `vaultProxy` / `MerkleAirdrop` / `Create2Factory`；带中文标签，供看板展示 |
| `indexer/config.js:watchContracts()` | 复用 `watchSources()` 的地址；**B08 部署记录缺失时只跳过该源**，不拖垮索引器（软依赖的保证） |
| `indexer/abi.js` | 事件注册表追加 B08 的 6 条事件签名（含 ERC-1967 的 `Upgraded`） |
| `scripts/02-acceptance.mjs` G 组 | 8 条断言，见下 |

## 三、G 组断言（跨项目对账的 8 条）

| 编号 | 断言 | 验的是什么 |
|------|------|----------|
| G-1 | 事件源清单含 B08 合约 | 联动的第一道门槛：配置真的生效了 |
| G-2 | `Upgraded` 事件已入索引且 ≥ 2 条 | 升级 + 回滚各一次，说明"实现版本史"完整 |
| G-3 | **B08 演练记录里的每个实现地址都能在索引里找到** | 跨项目对账：链上事件 ⟷ 演练快照 |
| G-4 | 最后一条 `Upgraded` 指向部署登记的 V1 实现 | 回滚收口：代码确实回到登记实现 |
| G-5 | 索引里出现过非登记实现地址 | 确实发生过升级到 V2（不是"只有一次空升级"） |
| G-6 | `Upgraded` 索引条数 == 链上 `eth_getLogs` 条数 | 链上独立复核，索引不漏不重 |
| G-7 | 看板按事件名可查升级证据 | 端到端：索引 → REST → 页面 |
| G-8 | `Claimed` / `Deployed` 也进索引 | 联动的第二个事件源（空投 + CREATE2） |

> **G-3 的方向性是刻意的**：升级演练每次跑都会部署一个**新的** V2 实现地址，
> 演练记录被覆盖后旧地址就查不到了。所以对账口径是
> 「演练记录里的每个实现地址都能在索引里找到」（新 ⊆ 旧索引），
> 而不是反过来（历史 V2 地址会因记录覆盖而丢失）。这个坑已写进代码注释。

## 四、两个看板各自能看到什么

```text
B08 运维看板 (8808)          B09 链上数据看板 (8802)
├─ 只读 RPC + 部署报告         ├─ 只读索引库 + REST
├─ 链状态/零 gas/终结性         ├─ 指标卡 / 事件分布 / 游标分页 / 持有人
├─ Gas 双指标表                ├─ 筛选：合同号 / 事件 / 批次 / Token / 地址
├─ 升级演练三快照              ├─ 事件名筛选可命中 Upgraded / Claimed / Deployed
├─ 大合约边界表                └─ 数据来源：B07 业务事件 + B08 工程事件
└─ 链上工程事件（实时 eth_getLogs）
```

两个看板是**互补**而不是重复：B08 看板读"链上真相"，B09 看板读"索引沉淀"。
前者能立刻反映链上当前状态，后者能回答"过去发生过什么"。

## 五、复现

```bash
# 1) 先跑 B08（升级演练会往链上写 Upgraded 事件）
cd projects/B08-合约工程化联盟网 && node scripts/run-all.js

# 2) 再跑 B09（验收会全量重扫，并把 B08 事件一起入库）
cd projects/B09-链上数据平台联盟网 && node scripts/02-acceptance.mjs

# 3) 起两个看板对照看
npm run serve                    # B08 → 127.0.0.1:8808
cd ../B09-链上数据平台联盟网 && npm run serve   # B09 → 127.0.0.1:8802
```

顺序不能反：B09 的 G 组要拿 B08 **最新**的演练快照对账，而快照由 B08 的 07 步产出。

> 注：即使顺序反了也不会挂——B09 验收脚本开头的 `scan.syncOnce()` 会增量追到链头，
> 新演练的 `Upgraded` 事件会被补进索引，对账仍然成立（实测 `REUSE_DB=1` 增量复跑 28/28 全绿，
> `Upgraded` 从 13 条涨到 15 条）。推荐顺序只是为了让对账语义最直观。
