## 实验 1 · 三节点 PoS 轮值出块并收敛

```
✓ 交易提交被接受
✓ 收敛 ｜ 高度 3/3/3，全网同一链尖
✓ 三节点账本一致 ｜ bob=250 于 3 个节点
✓ 轮值出现多个出块人 ｜ 3 个出块人轮转
✓ 手续费进入出块人账户
```

长时间运行（面板实测）：三节点同时到 **高度 343 / 权重 344**，链尖唯一、高度差 0，
每节点 `mined≈114 / received=343 / reorgs=0` —— 轮值共识下不产生竞争块。

## 实验 2 · 杀节点与重启追赶

```
（已关闭 victim 节点）
✓ 存活节点接受交易
✓ 离线期间链继续增长 ｜ 高度 3
✓ 重启节点追赶上链尖 ｜ 重启高度 3 vs 存活 3
✓ 追赶后账本一致 ｜ bob=42
```

要点：重启节点以**空链**启动，靠 `createNode` 的「冷启动追赶」向邻居要整条链、比权重后接受；
账本不是恢复出来的，而是**重放算出来的**——所以追赶后必然与邻居一致。

## 实验 3 · 人为分叉 → 最长链 → 已确认交易回滚（双花防护）

```
✓ 真的分叉了（同一高度不同块）
✓ 等重时不切换（防抖动）
✓ A 切换到更重链 ｜ 切换到更重链：4 → 6
✓ 被回滚的交易未入账 ｜ first=0
✓ 胜出分支的交易已入账 ｜ second=700
✓ 重组计数 ｜ reorgs=1
✓ 失败交易回到交易池等待重排 ｜ mempool=1
✓ 重排后双花仍然失败（nonce 已用）
```

这条是本项目最重要的实验：**同一笔钱（funder 的 nonce=0）在两条分支上各花一次**，
分区期间两边都「已确认」，重连后权重 4→6 的分支胜出，`first` 那笔 300 被回滚，
且回炉后因为 nonce 已被占用而**永远无法再次入账**。这就是「确认数」与「重组」的真实含义。

## 实验 4 · 非法交易一律被拒

```
✓ 篡改金额     ｜ HTTP 400 签名无效（报文被篡改）
✓ 篡改收款人   ｜ HTTP 400 签名无效（报文被篡改）

```

## 开发过程中真实踩到的两个坑（已修，写进单测/文档）

1. **`server.listen()` 后再 `once("listening")`**：本机端口几十微秒即就绪，监听器注册晚于事件 → 四个集成测试全部 25s 超时。
   修法：`server.listen(port, host, callback)`。
2. **交易池 `remove()` 只删索引不删主表**：已上链的交易被重复选中 → 下一块 nonce 冲突 → **节点永久出不了块**。
   修法：两张表都删 + 出块前在状态副本上预演过滤（这条预演让同类自锁不可能再发生）。
3. （测试卫生）端口写死导致两个测试进程抢端口出现假失败 → 改为按 `process.pid` 偏移。
