# 02 · 代理升级演练与存储槽冲突检查

> 代码：`src/UUPSUpgrade.sol`、`test/Upgrade.t.sol`、`script/Upgrade.s.sol`
> 验收对应 README：「代理升级演练含存储槽冲突检查」。

## 1. 结构：UUPS 里代理管地址、实现管权限

```
调用方 ──> ERC1967Proxy（只存实现地址 + 转发 fallback）
              │ delegatecall
              ▼
           VaultV1/V2（业务逻辑 + _authorizeUpgrade 权限门）
```

- 代理的全部「状态」其实存在**代理地址**下；实现合约是无状态的代码仓。
- 升级入口 `upgradeToAndCall` 在实现里，安全门 `_authorizeUpgrade` 是 `onlyOwner`——
  **谁能升级 = 业务权限问题**，UUPS 把它交给实现自己定义（Transparent 是代理上专职 admin，两者取舍见 §4）。
- 实现合约构造函数必须 `_disableInitializers()`：否则任何人可以直接在实现地址上
  `initialize` 抢 owner（测试 `test_implementationCannotBeInitialized` 钉死）。

## 2. 存储布局（forge inspect 实测，不是猜的）

| slot | VaultV1 | VaultV2（正确升级） | VaultBadV2（反例） |
|------|---------|--------------------|--------------------|
| 0 | owner | owner | owner |
| 1 | version | version | version |
| 2 | totalDeposited | totalDeposited（**位置不变**） | ⚠️ totalWithdrawn（插队占了 2） |
| 3 | gap | totalWithdrawn（吃 gap） | totalDeposited（被挤到 3） |
| 4 | gap | lastDepositBlock（吃 gap） | gap |
| 5+ | gap[46] | gap[44] | gap[45] |

**规则：新变量只能追加或吃 `__gap`，绝不能插在旧变量前面。** gap 的作用 =
给「将来想在中间加字段」预留的空槽，加完把 gap 缩短，尾部槽位不移动。

### OZ v5 的一个破除迷思点

v4 教程常说「slot 0 是 `_initialized`」——**v5 的 Initializable 已迁到 ERC-7201 命名空间存储**，
不占常规槽。本项目实测 `forge inspect VaultV1 storage-layout`：slot 0 直接是 `owner`。
以 inspect 输出为准，不以教程印象为准。

## 3. 槽冲突检查（测试怎么做的）

1. **固定槽 vs 状态槽零重叠**（`test_erc1967SlotsDoNotCollideWithStateSlots`）：
   手抄 EIP-1967 三个槽常量（实现 `0x3608…`、admin `0xb531…`、beacon `0xa3f0…`），
   `vm.load` 确认实现地址确实在标准槽、UUPS 模式下 admin/beacon 槽为空、
   状态槽 0/1/2 只含合约自己的数据。
   ⚠️ 坑：`StorageSlot.getAddressSlot(KECCAK).value` 读的是**调用者自己的存储**，
   查别的合约必须 `vm.load(address(target), slot)`——首版测试就栽在这里（读出 0）。
2. **升级前后逐槽对账**（脚本 `Upgrade.s.sol::upgradeToV2` 内置）：
   `before = vm.load(proxy, slot2)` → upgrade → `after = vm.load(proxy, slot2)`，
   不等直接 `require` revert。链上演练实测：`totalDeposited` 槽未变 ✓。
3. **布局 diff 门禁**（`test_layoutDiffGate`）：V1/V2 的 getter selector 逐一相等——
   改字段顺序的人会先挂测试再上链。
4. **反例复现**（`test_badUpgrade_slotCollisionRepro`）：用 BadV2 真实升级，
   断言「5 ether 的位还在 slot 2，但被 `totalWithdrawn` 读走、`totalDeposited` 读出 0」——
   **数据没丢，语义错位**，这就是存储槽冲突的事故形态。

## 4. 链上两步演练实测（anvil，2026-11-13）

```bash
# 第一步：部署 V1 实现 + 代理（零私钥：anvil 解锁账户）
forge script script/Upgrade.s.sol:UpgradeScript --sig "deployV1()" \
  --rpc-url http://127.0.0.1:8545 --broadcast --sender 0xf39F…2266 --unlocked
# → 代理 0x2E2Ed0Cf…，owner = 0xf39F…2266，version = 1

cast send <proxy> "deposit()" --value 1ether --unlocked --from 0xf39F…2266
# → totalDeposited = 1e18

# 第二步：升级（脚本内置槽2对账）
forge script script/Upgrade.s.sol:UpgradeScript --sig "upgradeToV2(address)" <proxy> \
  --rpc-url http://127.0.0.1:8545 --broadcast --sender 0xf39F…2266 --unlocked
# → "升级后 totalDeposited 槽未变 ✓"
```

升级后同地址读回：`totalDeposited = 1e18`（跨升级保留）、`totalWithdrawn = 0`（新字段）、
`owner` 不变、`version = 1`（migrate 前）、实现槽从 `0x21df54…` 换到 `0xdc11f7…`、
合约地址余额 1 ETH 仍在——**七项全对**。

## 5. UUPS vs Transparent 的一句话取舍

| | UUPS（本项目） | Transparent |
|--|----------------|-------------|
| 升级逻辑位置 | 实现合约（每个版本自带） | 代理（一次性写死） |
| 实现体积 | 多一个 `_authorizeUpgrade` | 更薄 |
| 误调用风险 | 实现上直接调业务函数会因非 delegatecall 失败（OZ v5 有 notDelegated 检查） | admin 调用被单独路由，业务函数对 admin 不可见 |
| 换权限规则 | 每次升级重新定义（灵活） | admin 固定（稳） | 

教学选 UUPS 是因为「升级权限 = 实现里的一个函数」这个概念最直观；生产选型看治理需求。
