> 配套：B08 侧说明见 [`B08/docs/07-B08与B09联动.md`](../../B08-合约工程化联盟网/docs/07-B08与B09联动.md)；

## 一、动机：索引器不只该盯业务数据

B09 最初的事件源是 B07 的两个合约（`LabCredential` 权益凭证 + `LabFaucet` 水龙头额度），
回答的是"**业务上发生了什么**"。

但联盟链上还有一类信息同样需要"可查询、可对账、可出证"：**运维动作的痕迹**。
B08 做的全部是工程动作，每一步都会在链上留痕：

| B08 的工程动作 | 链上事件 | 谁 emit | 索引价值 |
|----------------|----------|---------|----------|
| UUPS 代理升级 / 回滚 | `Upgraded(address indexed implementation)` | OZ `ERC1967Utils` | 代理的**实现版本史**——谁在什么时候把合约换成了什么 |
| Merkle 空投领取 | `Claimed(bytes32 indexed leafHash, address indexed to, string data)` | `MerkleAirdrop` | 发放与领取的留痕，可与链下出证包对账 |
| CREATE2 落址 | `Deployed(address indexed addr, bytes32 indexed salt, uint256 deployCount)` | `Create2Factory` | 地址登记簿：哪个 salt 落到了哪个地址 |
| Vault 出金 | `Withdrawn(address indexed who, uint256 amount)` | `VaultV2` | 业务事件（当前演练未触发） |
| 账户抽象执行 | `Executed` / `HandleOp` | B08 `AccountAbstraction` | 4337 概念裁剪的执行痕迹 |

只做 B09 不带 B08，索引出来的是"业务数据"；带上 B08，索引出来的是"业务数据 + 运维证据"。

## 二、实现（B09 侧改了三个文件）

### 1. `indexer/config.js`：事件源清单化

```js
export function watchSources() {
  const out = [];
  const b7 = readDeployment("B07-NFT市场联盟网");   // 业务源
  if (b7) {
    if (b7.credential) out.push({ label: "LabCredential（权益凭证）", address: b7.credential });
    if (b7.faucet) out.push({ label: "LabFaucet（水龙头额度）", address: b7.faucet });
  }
  const b8 = readDeployment("B08-合约工程化联盟网"); // 工程源（联动）
  if (b8) {
    if (b8.vaultProxy) out.push({ label: "Vault 代理（UUPS 升级证据）", address: b8.vaultProxy });
    if (b8.MerkleAirdrop) out.push({ label: "Merkle 空投", address: b8.MerkleAirdrop });
    if (b8.Create2Factory) out.push({ label: "Create2 工厂", address: b8.Create2Factory });
  }
  return out;
}
```

**软依赖的保证**：B08 的部署记录读不到就**只跳过该源**（`readDeployment` 返回 `null`），
索引器不会因此失败。也就是说 B08 不是 B09 的隐性前置条件——它是**增强项**。

### 2. `indexer/abi.js`：事件注册表追加 B08 的 6 条签名

```js
  // ── B08 合约工程事件（B08 × B09 联动的第二个事件源）──
  "event Upgraded(address indexed implementation)",                        // ERC-1967
  "event Claimed(bytes32 indexed leafHash, address indexed to, string data)",
  "event Deployed(address indexed addr, bytes32 indexed salt, uint256 deployCount)",
  "event Withdrawn(address indexed who, uint256 amount)",
  "event Executed(uint256 indexed nonce, bytes4 selector)",
  "event HandleOp(address indexed sender, uint256 nonce)",
```

解码与过滤列抽平逻辑复用同一套（`decodeLog` → `decoded` JSON + `fromAddr/toAddr/tokenId/batch`），
所以 B08 的事件进了库就能用同样的筛选维度查（按合同号、按事件名、按地址、按 txHash）。

### 3. `scripts/02-acceptance.mjs`：新增 G 组（8 条断言）

验收脚本原先只扫 `[dep.credential, dep.faucet]`，现在改成 `watchContracts()`（5 个源）。

## 三、跨项目对账：G 组到底在验什么

这是整个联动里最有价值的一条链：

```text
B08 升级演练（脚本 07）
   └─ 链上：upgradeToAndCall(V2) → upgradeToAndCall(V1)
   │     emit Upgraded(V2) / Upgraded(V1)
   └─ 落盘：deployments/upgrade-drill.json
              snapshots[0].impl = V1（before）
              snapshots[1].impl = V2（after-upgrade）
              snapshots[2].impl = V1（after-rollback）
                    │
                    ▼
B09 索引器（扫块 → 落库）
   └─ logs 表：eventName='Upgraded'，decoded={"implementation":"0x…"}
                    │
                    ▼
B09 验收 G 组
   ├─ 演练记录里的每个实现地址 ⊆ 索引里的实现地址   ← 跨项目对账
   ├─ 最后一条 Upgraded == 部署登记的 V1（回滚收口）
   ├─ 存在非登记实现地址（确实升到过 V2）
   └─ 索引条数 == 链上 eth_getLogs 条数            ← 链上独立复核
```

**为什么对账方向是「演练记录 ⊆ 索引」而不是反过来**：
每次 B08 演练都会**新部署**一个 V2 实现（地址每次都不同），演练记录是覆盖写的。
历史 V2 地址会随记录覆盖而从 JSON 里消失，但它们**永远留在链上和索引里**。
所以只能反着断言：新演练记录里的地址，必须能在历史索引里找到。

**G 组实测结果（2026-11-13）**：

```text
[PASS] 事件源清单含 B08 合约（5 个源）
[PASS] ERC-1967 Upgraded 已入索引（13 条）
[PASS] B08 演练记录里的每个实现地址都能在索引里找到（0xe87a99b7… / 0x475e65a0…）
[PASS] 回滚收口：最后一条 Upgraded 指向部署登记的 V1 实现（0xe87a99b7…）
[PASS] 确实发生过升级到 V2（7 个非登记实现地址）
[PASS] Upgraded 事件数与链上 eth_getLogs 一致（13 == 13）
[PASS] 看板按事件名可查升级证据（13ms，13 条）
[PASS] B08 空投/CREATE2 事件也进索引（Claimed=3 条，Deployed=3 条）
```

## 四、看板侧的效果

B09 看板的筛选栏里，`事件` 一栏现在可以直接填：

- `Upgraded` → 代理升级证据（含实现地址）
- `Claimed` → 空投领取
- `Deployed` → CREATE2 落址
- `CredentialIssued` / `Payout` / `TransferBlocked` → B07 的业务事件

也就是**同一个看板、同一个游标分页、同一个筛选维度**，里既有业务流水也有运维痕迹。

## 五、复现顺序（推荐先 B08 后 B09）

```bash
# 1) 先跑 B08（升级演练会往链上写新的 Upgraded 事件，并刷新 upgrade-drill.json）
cd projects/B08-合约工程化联盟网 && node scripts/run-all.js

# 2) 再跑 B09（验收全量重扫，把 B08 的事件一起入库，并用最新演练快照对账）
cd projects/B09-链上数据平台联盟网 && node scripts/02-acceptance.mjs
```

**顺序反了会不会挂？** 实测不会：验收脚本开头会同步到链头，新 V2 的 `Upgraded` 会被补入；随后再执行跨项目对账。

但**推荐**先跑 B08：对账语义最直观——用最新演练快照对最新索引。当前默认每次新建独立验收库，不删除旧库；只有显式指定 `DB_PATH` 做增量调试时才使用 `REUSE_DB=1`。最新全量结果（含 B05/B06 与源指纹重扫）为 **48/48**，见 [02-验收记录](./02-验收记录.md)。

## 六、还没做的

1. **出证口径**：`shared/evidence` 的 schema v1.1 还没有 `finalityModel: "qbft-certificate"` 字段，
   QBFT 终结性的出证要等它（B09 索引的事件现在只能"查"，还不能按联盟链口径"出证"）。
2. **事件注册表自动生成**：22 条签名仍是手写（与 P09 同款技术债），应从 `abi/*.json` 生成。
3. **派生状态对 B08 无意义**：B08 的事件没有 `Transfer` 语义，`assets`/`holders` 派生表对它们是空的——
   这是对的（工程事件不涉及资产），但表结构将来若要支持"非资产合约"，需要显式区分。
