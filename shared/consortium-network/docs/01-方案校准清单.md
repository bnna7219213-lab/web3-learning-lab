## 二、逐条详解

### 1 IBFT 2.0 → 应该用 QBFT ❌

官方原文（`docs/private-networks/how-to/configure/consensus/ibft.md` 第 12 行）：

> "IBFT 2.0 is supported for existing private networks, but **QBFT is the recommended enterprise-grade consensus protocol for private networks**."

投标语境下这条还有一层意义：QBFT 是 IETF 标准化的算法（`migrate-from-ibft-to-qbft.md` 存在本身就说明 IBFT 是历史包袱）。**新项目没有理由选 IBFT**，除非客户已有 IBFT 链要接进去。

### 2 下载地址失效 ❌

实测（`curl -sIL`）：

| URL | 结果 |
|-----|------|
| `artifacts.consensys.net/public/besu/raw/names/besu.tar.gz` | **404** |
| `artifacts.consensys.net/public/go-quorum/raw/names/besu/versions/24.10.0/besu-26.9.0...`（原方案那条） | **404** |
| `github.com/hyperledger/besu/releases/download/26.9.0/besu-26.9.0.tar.gz` | **200** ✅ |

离线内网交付时正确做法：外网机下载 `besu-26.9.0.tar.gz` **和 `besu-26.9.0.tar.gz.sha256`**，校验后带入。见 `scripts/00-preflight.sh` 的校验逻辑。

### 3 Post-Merge 区块常量 ❌

官方（qbft.md「Post-Merge configuration」）要求这些字段**必须**是常量：

| 字段 | 必须的值 |
|------|----------|
| `ommersHash` | `0x1dcc4de8dec75d7aab85b567b6ccd41ad312451b948a7413f0a142fd40d49347` |
| `difficulty` | `0`（被 `prevrandao` 取代）← 你写的是 `"0x1"` |
| `mixHash` | `0x0000…0000`（32 字节全零）← 你的 genesis 里没有 |
| `nonce` | `0x0000000000000000` |
| `ommers` | `[]` |

且 `extraData` 在 Merge 后**只允许 32 字节 vanity**（其余由 QBFT 编码验证者列表与 round）。修正版见 `genesis/qbft-genesis.json.tpl`。

### 4 零 gas 的正确配方 ❌（你写错了机制）

官方 free-gas 六步，你的方案只做了第 4 步的一半：

| 步 | 官方要求 | 你的方案 |
|----|----------|----------|
| 1 | `gasLimit: 0x1fffffffffffff`（Hardhat 可接受的最大值） | ✅ 有 |
| 2 | 需要大交易时设 `pertxgaslimit`（EIP-7825 把单笔上限压到 16,777,216 gas） | ❌ 无 → **P08 的大合约可能部署不进去** |
| 3 | `contractSizeLimit: 2147483647` | ❌ 无 |
| 4 | `--min-gas-price=0`（**每个节点都要设**） | ⚠️ 只写在文字里，config 没给 |
| 5 | `--tx-pool-enable-balance-check=false` | ❌ 无 |
| 6 | 用了 `londonBlock` 就必须 `"zeroBaseFee": true` | ❌ 你写的是 `baseFeePerGas: 0x0`，**不是官方机制** |

官方 danger 提示值得单独抄进 Runbook：

> "Any node with a minimum gas price set higher than zero will **silently drop** transactions with a zero gas price."

即：4 个验证者里有 1 个忘了设 `min-gas-price=0`，交易就会**无声消失**——这是最难查的一类故障（没有报错，只有"交易不见了"）。

第 5 步对联盟场景尤其关键：成员方很多账户余额为 0（运营方代付 gas 或不计费），默认 `true` 会让它们的交易进不了 txpool 优先层。

### 5 `rpc-http-apis` 键名错 ❌

`docs/public-networks/reference/options.md` 里是 **`rpc-http-api`**（出现 7 次；`rpc-http-apis` 仅 1 次，疑为文档笔误）。Besu 解析 config.toml 时遇到未知键会**直接拒绝启动**——所以这不是风格问题，是"起不来"。

### 6 硬件：超配一个数量级 ⚠️

官方 `system-requirements.md`：私有网"volume 远低于主网，因此要求更低"；**JVM 最低 4GB**，推荐 VM **6GB 内存 / 10–20GB 磁盘**，验证者与 RPC 节点用**本地 SSD**。

你的表：Validator 8C/32GB/500GB NVMe ×4 + RPC 16C/64GB/1TB ×2 ≈ **208GB 内存、4TB NVMe**。

报价影响：这套配置在政企投标里会直接被质疑预算。**正确做法是先给"够用档"再给"富余档"**：

| 档 | Validator ×4 | RPC ×2 | 说明 |
|----|--------------|--------|------|
| 起步（POC/试点） | 4C/8GB/200GB SSD | 4C/16GB/500GB SSD | 对齐官方建议，够用 |
| 生产（TPS 敏感） | 8C/32GB/1TB NVMe | 16C/64GB/2TB NVMe | 你的原表，但要有**压测数据**支撑 |

选档依据必须是 `scripts/30-smoke-test.sh` + spamoor 压测的实测 TPS，不是拍脑袋。

### 7 "无分叉风险" 要改成可验证的承诺 ⚠️

QBFT/IBFT 是**确定性终结**：一旦提交不可回滚，这点你说对了。但要一并说清可用性边界：

- n=4 → f=1，**quorum = 2f+1 = 3** → 挂 1 台正常，**挂 2 台停链**
- 所以"4 台最小"的代价是**没有维护余量**：滚动升级必须一次只停 1 台
- 想要"停 2 台还能出块"，需要 n=7（f=2，quorum=5）

这是给客户讲 SLA 时必须算清楚的数，不是"无风险"三个字。

### 8 性能瓶颈那 4 个百分比 ❓

没有出处，且方向不对。QBFT 每块要跑一轮 **prepare/commit 两阶段、消息量 O(n²)**，所以**验证者数量**才是第一限制；其次是磁盘 I/O（状态读写）与网络往返延迟（跨机房部署时 round-trip 直接决定出块时间）。

交付时的正确表述：**"验证者建议 ≤7 台，跨机房 RTT 建议 <50ms，出块时间取 RTT 的 3–5 倍"** ——并说明这是需要压测验证的经验值，不是承诺。

### 9 防火墙自相矛盾 ⚠️

同一段里既 `rpc-http-host="127.0.0.1"`（只绑本机），又 `firewall-cmd --add-port=8545/tcp`（对全网开放）。前者让后者无意义，但如果哪天有人把 host 改成 `0.0.0.0` 图方便，端口是现成开着的。

修正：RPC 只在 **RPC 节点**开放，且 `--add-source=<运维/成员子网>`；`metrics-host` 同理限源。见 `scripts/` 与 `docs/03-成员接入与权限治理.md`。

| 项 | 文档/我的假设 | 服务器实测 |
|----|---------------|------------|
| Java 版本 | preflight 写"需 JDK 17+"（照抄常见说法） | **Besu 26.9.0 要求 Java 25+**；已从 JDK 24 升到 Oracle JDK 25.0.4.1 LTS |

> 教训：官方 `system-requirements.md` 只写 JVM 内存不写 JDK 版本，所以"JDK 17"这类数字**必须以实际启动报错为准**。已把 preflight 改成 `REQUIRED_JAVA=25` 且可覆盖。

### 我自己在上一轮交付里写错的 4 个选项名（全部已修）

Besu 对**未知 CLI 选项与 config.toml 未知键都是直接拒绝启动**，所以这四个都是致命级：

| 我写的 | 真实选项 | 出现位置 | 怎么查出来的 |
|--------|----------|----------|--------------|
| `--qbft-enabled=true` | **不存在**（QBFT 由 genesis 的 `"qbft"` 段启用；`QBFT` 只是 RPC API 命名空间名） | docker-compose ×4、validator.toml、rpc.toml | `grep -c qbft-enabled` 在 popts/qbft/ibft 三份文档中均为 0 |
| `--p2p-ip=` | `--p2p-host=` | docker-compose ×4 | `## \`p2p-ip\`` 无官方小节，`p2p-host` 有 |
| `rpc-http-gas-cap` | `rpc-gas-cap` | config/rpc.toml | 同上 |
| `PERMISSIONING`（RPC API 名） | `PERM` | compose、validator.toml、21-up-native.sh | 官方 `--rpc-http-api` 合法值列表：`ADMIN, DEBUG, ENGINE, ETH, IBFT, MINER, NET, PERM, PLUGINS, QBFT, TRACE, TXPOOL, WEB3` |

**为什么值得写出来**：这三个都是我"看起来合理"就写下的，和上一轮 `eth_getFinalizedBlock`、`cast wallet new-mnemonic` 是同一类错误。
现在的固定动作是：**写完任何命令行，用 `grep "^## \`选项名\`"` 在官方 options 参考里逐个验一遍**——这次就是靠这一步抓出来的。

### 一条重要的 QBFT 运维事实（官方 danger，之前我没写）

> "If more than 1/3 of validators stop participating, new blocks can no longer be created and
> `requesttimeoutseconds` doubles with each round change.
> **The quickest method to resume block production is to restart all validators**, which resets `requesttimeoutseconds` to its genesis value."

含义：n=4 时挂 2 台（=1/2 > 1/3）就停链，且**恢复后不会自动快起来**——超时时间已经指数翻倍。
正确恢复动作是**重启全部验证者**让它回到 genesis 的 timeout，而不是"把挂掉的那台补上"就完事。
这条直接进 SLA 与 Runbook，见 `docs/03` 与本文件下方。

另外官方给的调参法则也确认了我的 genesis 取值合理：`requesttimeoutseconds` 取 `blockperiodseconds` 的 **2 倍**（5 / 10 ✓）。
