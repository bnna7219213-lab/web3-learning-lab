# 03 · 成员接入与权限治理

> 这一章回答 B 分支的核心命题："**去中心化联盟账户成员**"到底怎么落地。
> 依据 Besu `docs/private-networks/concepts/permissioning.md` 与 `how-to/configure/consensus/qbft.md`（2026-10-14）。

## 一、三个不同层次的"权限"，别混

| 层次 | 控制什么 | Besu 机制 | 典型事故 |
|------|----------|-----------|----------|
| **网络层** | 谁能连 P2P | `nodes-allowlist`（enode） | 只开这层 → 别人仍能直连 RPC 发交易 |
| **账户层** | 谁能发交易 | `accounts-allowlist` 或链上权限合约 | 开了这层却忘了合约部署者地址 → P04 之后全卡住 |
| **验证层** | 谁出块 | QBFT 验证者集合（header 投票 或 合约） | 用 `extraData` 固定后想加验证者 → 必须走 epoch 边界 |

**你的方案里"白名单控制节点和账户接入"是对的，但没说明"白名单挡不住 RPC 直连"这一条。**

## 二、成员接入 SOP（可写进交付文档）

```text
① 申请：成员提交 机构名 / 责任人 / 节点 IP / 用途（只读 or 发交易 or 出块）
② 审核：运营方核身份 → 决定授权范围（三档，见下表）
③ 生成：成员本机 besu 生成节点密钥 → 导出 enode（公钥，不含私钥）
④ 授权：运营方写入 nodes-allowlist（文件热加载 或 链上合约 addNode）
⑤ 分发：genesis.json（逐字节一致）+ bootnodes + 接入手册
⑥ 同步：成员起节点 → 观察 eth_blockNumber 追平 → 记录首次同步耗时
⑦ 验证：30-smoke-test.sh 通过 + peer 数 ≥1 + 出证接口能查到该成员节点
⑧ 留痕：授权时间、授权人、enode、审批单号 → 这本身就是一条 M4 存证
```

### 三档授权（对应不同收费）

| 档位 | 能力 | 适用 | 计费 |
|------|------|------|------|
| 只读成员 | 连网同步、查自己的数据 | 审计方、监管节点、下游客户 | 按账户年费 |
| 交易成员 | 可发交易（白名单账户）、部署合约 | 业务参与方 | 按账户 + 流水 |
| 验证成员 | 参与出块（QBFT 验证者） | 核心链主/行业协会 | 资源分摊 + 治理责任 |

> 变成验证成员是**改 genesis/epoch 级别的动作**，不是开关：n 从 4 变 5 会改变 quorum（4→4）。
> 这条必须写进合同，否则客户会以为"随时可以加我们自己的节点出块"。

## 三、文件白名单 vs 链上权限合约

| | 文件（`permissions_config.toml`） | 链上合约（`AdminContract.addNode`） |
|--|-----------------------------------|--------------------------------------|
| 变更速度 | 需分发+重启/热加载 | 一笔交易，秒级 |
| 可审计性 | 散落在各台机器的文件里 | **天然留痕**：谁、何时、授权了谁 |
| 一致性风险 | 高（某台没同步就分区） | 低（状态在链上） |
| 适合阶段 | POC、试点 | 生产、多成员 |

**建议**：POC 用文件（快），生产上链上合约（可审计），并把"授权动作"本身纳入 M4 出证范围。

## 四、验证者管理（QBFT 两种方式）

| 方式 | 加验证者 | 适用 |
|------|----------|------|
| Block header（extraData） | `qbft_proposeValidatorVote` 现有验证者投票，**epoch 边界生效** | 成员固定、变更少 |
| Smart contract | 合约读写即时生效（`validatorcontractaddress` 指向合约） | 成员频繁进出、需要治理流程 |

注意：`epochlength` **上线后不可改**（官方：改了会产生非法块）。所以一开始就要按"未来会不会扩验证者"来定 `epochlength`。

## 五、RPC 暴露的正确姿势

```text
成员/前端 ──HTTPS+Token──▶ 反向代理（限流、鉴权、审计日志）
                              └──▶ RPC 节点 :8545（只绑内网网卡）
                                      └── P2P ──▶ 验证者（RPC 只绑 127.0.0.1）
```

- 验证者的 8545 **永远不给成员直连**（`config/validator.toml` 里 `rpc-http-host="127.0.0.1"`）
- 成员的防火墙规则用 `--add-source=<子网>`，不要 `--add-port` 全开
- 需要外网访问时：只暴露代理，代理做 mTLS 或 token，并记录"谁调了什么方法"（这是 M4 的审计数据源）

## 六、停链与恢复（QBFT 特有的运维事实）

官方 danger 原文：

> "If more than 1/3 of validators stop participating, new blocks can no longer be created and
> `requesttimeoutseconds` doubles with each round change.
> **The quickest method to resume block production is to restart all validators**, which resets `requesttimeoutseconds` to its genesis value."

对 n=4 的直接含义：

| 场景 | 结果 | 正确动作 |
|------|------|----------|
| 1 台宕机 | 继续出块（quorum=3 满足） | 报警但无需干预；**不要**同时维护第 2 台 |
| 2 台宕机 | **停链**（2/4 > 1/3 失效） | 拉起宕机节点后，**重启全部 4 台**以复位 request timeout |
| 全部恢复后仍不出块 | 超时已指数翻倍 | 同上：全量重启，而不是干等 |
| 滚动升级 | 一次只能停 1 台 | 4 台无维护余量；要"停 2 台仍可用"需 n=7 |

写进 SLA 的表述：**"联盟链可用性 = 成员在线率的函数；n=4 时单节点故障容忍 1 台，恢复流程要求全量重启验证者，预计影响 ≤ X 分钟。"**
调参依据（官方）：`requesttimeoutseconds = 2 × blockperiodseconds`；本底座取 5 / 10。

## 七、和 P 分支最实质的差别

P 分支（Sepolia/anvil）里，"谁能发交易"由**私钥持有**决定；
B 分支里，"谁能发交易"由**运营方授权**决定 —— 这是联盟链的真实价值，也是它的真实风险：

> 运营方一旦掌握账户白名单，就掌握了"谁能用这条链"。
> 因此授权动作必须可审计、可申诉、有 SLA，否则客户会问："那和你直接给我一个数据库有什么区别？"

回答这个问题的方式不是技术，是流程：**链上权限合约 + 授权留痕 + 客户方共同管理密钥**。
