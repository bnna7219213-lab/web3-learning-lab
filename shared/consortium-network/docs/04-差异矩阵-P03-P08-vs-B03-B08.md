# 04 · 差异矩阵：P03–P08（公链/anvil）vs B03–B08（联盟 QBFT）

> 原则：**功能实现一样，环境语义不一样**。每往下一行，都要回答"多成员、零 gas、确定性终结、白名单准入"这四件事改变了什么。

## 一、六个分支的对照

| 分支 | 对应 P | 同一件事 | B 分支额外要证明的 |
|------|--------|----------|---------------------|
| **B03** | P03 链上交互 | 交易生命周期逐字段解析 | 无公网浏览器 → **自建 Blockscout/内网解析器**；`chainId` 自定义；RPC 限源；确定性终结下"确认数"语义变化 |
| **B04** | P04 HelloContract | 写-测-部署闭环 | 部署到 QBFT 链：`--rpc-url` + `chain-id` profile；**零 gas 下 gas 估算行为不同**；部署者必须在账户白名单 |
| **B05** | P05 ERC20 | 代币与权限 | 联盟内部积分/权益代币的**角色治理**：谁可 mint/burn，跨成员授权；`pertxgaslimit` 对大合约的影响 |
| **B06** | P06 投票 DApp | 合约+前端闭环 | **多成员账户体系**：每成员独立账户与 nonce；前端要能切成员；审批流 = 双人复核（对应 M5） |
| **B07** | P07 NFT 市场 | 铸造/挂单/成交 | 联盟内权益凭证流转：成员间转让受账户白名单约束；元数据放**内网对象存储**而非公网 IPFS |
| **B08** | P08 合约工程化 | Gas/升级/Create2/Merkle | **零 gas 下 Gas 优化的意义重定义**（从"省钱"变"省区块容量与延迟"）；大合约受 `contractSizeLimit`/EIP-7825 约束；升级演练要全成员参与 |

## 二、四个环境语义差异，逐条落到工程上

### 1 多成员：nonce 与账户归属

| | P 分支 | B 分支 |
|--|--------|--------|
| 账户来源 | 一个学习钱包（anvil 0 号） | 每成员一组账户，由运营方授权 |
| nonce 管理 | 单账户顺序即可 | **每账户独立 nonce**；并发脚本必须按账户分片，否则互相挤掉 |
| 故障表现 | 交易 pending | 交易被后到的同 nonce 顶掉，表现为"偶尔丢单" |

工程要求：B 分支所有脚本/前端统一走 **nonce 管理器**（按 address 串行化 + 失败重试），这是 P 分支可以偷懒、B 分支不能偷懒的地方。

### 2 零 gas：估算与失败模式

- `eth_estimateGas` 仍工作（gas 有用量，只是价格为 0）
- `eth_gasPrice` 必须返回 0；否则说明某节点配置漂移（见 `docs/02`）
- MetaMask 等钱包在零 gas 链上会**拒绝或提示异常**（它按非零 baseFee 校验）→ 交付时前端用 viem 自己构造交易并显式设 `maxFeePerGas: 0`
- 大合约部署：受 EIP-7825 单笔上限约束 → 需 `pertxgaslimit`（见 `genesis/qbft-genesis.json.tpl`）

### 3 确定性终结：把"确认数"改成"终结证明"

| | 公链（Sepolia） | QBFT 联盟链 |
|--|-----------------|-------------|
| 回滚可能 | 有（重组） | 提交后无 |
| 出证口径 | `N 个确认后出证` | **`区块被 QBFT 证书终结` + 出证时带 blockHash/txRoot** |
| 停链风险 | 低 | **有**：n=4 挂 2 台即停 |
| 出证 SLA | 延迟 = N × 出块时间 | 延迟 = 出块时间（5s），但可用性 = 成员在线率 |

这直接影响 `shared/evidence` 出证契约：`anchor` 里应允许 `finalityModel: "qbft-certificate" | "n-confirmations"`。
→ 待办：把这条加进出证 schema v1.1（当前 schema 只有 `confirmationsRequired`）。

### 4 白名单准入：安全边界从密码学变成流程

| 风险 | P 分支 | B 分支 |
|------|--------|--------|
| 私钥泄露 | 资产损失 | 资产损失 **+ 该成员可继续发交易直到被吊销** |
| 运营方作恶 | 不可能（链不属于你） | **可能**（能改白名单）→ 必须用链上合约 + 多签 + 留痕对冲 |
| 外部攻击者 | 需破解密码学 | 需拿下成员账户或 RPC 入口（所以 RPC 限源与代理鉴权是主战场） |

## 三、B 分支共用的验收增量（每个 B0x 的 README 都要带这四条）

1. [ ] **多成员视角**：至少 2 个不同成员账户各自发起交易，互不干扰（nonce 不串）
2. [ ] **零 gas 断言**：`eth_gasPrice == 0` 且 `baseFeePerGas == 0`，且交易确实入账
3. [ ] **终结性断言**：交易所在块的 `blockHash` 在 3 个节点上查询结果一致，且 5 分钟后仍一致
4. [ ] **权限负例**：未授权账户/未授权节点被拒，并留下可审计记录（这条是 P 分支根本没有的维度）

## 四、什么情况下 B 分支是多余的

诚实判断：**如果客户只有 1 家机构、且不需要多成员共同记账，就不要做 B 分支**——
那用一个私有单节点 Besu 或直接 anvil 交付即可，多出来的成员治理、白名单、终结性证明全是净成本。
B 分支的存在意义 = "**多个互相不完全信任的主体，要在同一份账本上协作**"。这句话不成立，方案就不成立。
